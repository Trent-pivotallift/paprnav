## Blocking findings

1. **Correction ordering has no real tiebreaker, so "latest correction" is not actually deterministic.** `OCRTextSpan.corrections` is now ordered by `order_by="OCRCorrection.created_at"` only, and both `effective_span_text()` and `add_entry_evidence()` rely on `span.corrections[-1]` to decide which correction is authoritative. `created_at` is populated via `server_default=func.now()`. On Postgres (the real backend per `docker-compose.yml`), `now()`/`CURRENT_TIMESTAMP` returns the *transaction* start time, not per-statement time, so any two `OCRCorrection` rows inserted in the same transaction get an identical timestamp; on SQLite (tests), I confirmed `CURRENT_TIMESTAMP` has 1-second resolution, so rows inserted in the same second tie too. `OCRCorrection.id` is a random UUID (`new_id("cor")`), so it can't serve as a secondary sort key either. Today's single-correction-per-request flow mostly avoids hitting this, but nothing prevents a future bulk-correction/backfill/retry path from creating >1 correction for the same span in one transaction, and when that happens `corrections[-1]` becomes DB/plan dependent rather than "the correction the reviewer most recently applied." This is exactly the property the audit trail is supposed to guarantee. Needs a monotonic tiebreaker (autoincrement/sequence column, or at minimum `order_by=(created_at, id)` with a sortable id) rather than relying on wall-clock time alone.

2. **No test actually exercises a content-changing correction.** In `test_ocr_ingestion_verification_correction_and_entry_extraction`, the correction is posted with `"correctedText": low_confidence_spans[0]["text"]` — i.e. identical to the original text. This is a no-op "correction." Consequently nothing verifies:
   - that the raw `OCRTextSpan.text` stays byte-for-byte unchanged while a *real* edit propagates into the derived `LogbookEntry` field, and
   - that when two corrections exist for one span, the second (later) one wins for both `effective_span_text()` and the evidence row's `ocr_correction_id`.
   The two properties this task asks to verify most ("raw spans remain raw" and "corrections represented correctly") are only true by code inspection, not by test.

3. **`entry_date` can be populated from a silent fallback with zero evidence.** `parse_date()` defaults to `datetime.now(timezone.utc).date()` when the first line doesn't match `DATE_PATTERN`, but `extraction_field_spans()` only emits an `entry_date` evidence row when the pattern *does* match. So a garbled/OCR-misread date can end up on a persisted `LogbookEntry.entry_date` with no evidence link at all and no signal that it's a fallback guess rather than an extracted value — the one field most likely to be audited.

4. **`.ai/DATA_MODEL.md` wasn't updated to match the field_name values this change actually writes.** `LogbookEntryEvidence.field_name` doc still lists `entry_date, description, performer_name, performer_credential, tach_time, other`, but the code now writes `hobbs_time` and `total_time` verbatim rather than folding them into `other`. Since this diff is what introduces multi-field evidence, the doc should be updated alongside it (it's included in this review precisely because it's supposed to be the contract).

## Questions

- In `create_ocr_correction` (route, unchanged by this diff but relevant context), `original_text` is always snapshotted from `span.text` (the raw OCR text), even for a second/third correction on the same span. Is the correction history intentionally "always vs. raw" rather than a chained diff against the prior correction? Worth confirming this is deliberate given point 1 above.
- `extraction_field_spans()` unconditionally adds a `performer_credential` evidence row whenever a "Performer:" line is found, even when `parse_performer()` returns `credential=None`. Is an evidence row for a field that ends up `NULL` on the entry intentional?
- `find_float_field_span`/`find_line_span` re-implement the same regex/prefix logic already in `parse_float_field`/`parse_performer`, in a second place. If these two implementations ever drift, the evidence link would point at a span that doesn't actually correspond to the stored value. Any reason not to have the `parse_*` functions return `(value, span)` together instead of matching twice?
- `field_name` remains an unvalidated free string end-to-end (DB `String(128)`, no Pydantic enum). Given it's the audit-trail key, is validation planned, or is it deliberately left open for future field types?
