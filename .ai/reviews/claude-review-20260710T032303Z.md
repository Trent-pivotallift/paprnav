# Code Review: paprnav AWS pilot + Textract/OpenAI ingestion

## 1. Findings

Ordered by severity. All line references are against the working tree.

### High

**H1 — Deploy IAM role can delete/rewrite any KMS key in the account (data-loss risk)**
`infra/aws-iam/paprnav-terraform-deploy-policy.json`, `KmsForPaprnNavManagedKeys` statement grants `kms:ScheduleKeyDeletion`, `kms:PutKeyPolicy`, `kms:DeleteAlias`, `kms:UpdateAlias`, etc. on `"Resource": "*"`. `kms:CreateKey`/`ListAliases` legitimately require `*`, but destructive/policy-mutating actions on `*` mean a compromised or buggy apply could schedule deletion of unrelated account KMS keys. Scope the destructive actions with a condition (e.g. `aws:ResourceTag/Project = paprnav`) or a dedicated key ARN, and split them out from the create-only statement. `secretsmanager:*` (full, incl. delete) is scoped to `paprnav-*` which is acceptable, but the KMS grant is the outlier.

**H2 — Consent is not enforced server-side before OCR processing (privacy/billing)**
`backend/app/api/routes/uploads.py` `upload_logbook_file` accepts `pilotConsentAccepted: bool = Form(default=False)` and unconditionally stores the file and enqueues ingestion; consent only flips `billing_status` to `not_billable` in `ingestion.py` (`process_ingestion_job`). The frontend disables the button (`upload/page.tsx`, `disabled=... || !pilotConsentAccepted`), but any direct API call with `pilotConsentAccepted=false` (or omitted) still uploads volunteer maintenance data and incurs Textract cost. If consent is meant to gate processing of volunteer data, enforce it in the endpoint (reject with 4xx when false), not just in the UI.

### Medium

**M1 — Terraform `use_lockfile` vs `required_version = ">= 1.6.0"` mismatch**
`infra/terraform/versions.tf`: the S3 backend uses `use_lockfile = true` (S3-native state locking), which is only available in Terraform ≥ 1.10 (stabilized 1.11). With `required_version = ">= 1.6.0"`, a 1.6–1.9 CLI will either error on the backend arg or run without state locking — concurrent applies could corrupt remote state. Bump `required_version` to `>= 1.11.0` (or add a DynamoDB lock table for older CLIs).

**M2 — S3 lifecycle never expires noncurrent versions of real uploads (cost + retention)**
`infra/terraform/main.tf` `aws_s3_bucket_lifecycle_configuration.app_artifacts`: the rule is filtered to `prefix = "tmp/"`, and the `noncurrent_version_expiration { noncurrent_days = 30 }` lives *inside* that filtered rule. The bucket has versioning Enabled, so noncurrent versions and delete markers of the actual uploaded logbooks (non-`tmp/`) accumulate indefinitely — unbounded storage cost and an open-ended retention footprint for volunteer PII. Add an unfiltered rule (or separate rule) for `noncurrent_version_expiration` and `abort_incomplete_multipart_upload`.

**M3 — Per-customer cost-allocation tags won’t actually appear in AWS billing as designed**
`backend/app/services/cost_tags.py` stamps `CustomerAccount`/`Aircraft`/`BillableAccount` as S3 object tags (`store_s3_file` `Tagging=...`), and `main.tf` sets ECS default tags. But: (a) user-defined cost allocation tags must be *activated* in the Billing console — nothing in Terraform does this; (b) the budget (`aws_budgets_budget.monthly_pilot`) filters only on `user:Project`; (c) Textract charges cannot be tagged per request, so per-customer/per-aircraft OCR spend is **not** derivable from AWS cost allocation tags at all — only from the app-side `OCRRun.billable_page_count`. This is fine as an app-side billing model, but the tag plumbing gives a false impression that AWS Cost Explorer will break OCR spend down per customer. Worth documenting/reconciling with `AWS_PILOT_TERRAFORM_PLAN.md`.

**M4 — S3 download branch is untested and may not stream correctly**
`backend/app/api/routes/uploads.py` `download_upload` returns `StreamingResponse(response["Body"], ...)` where `Body` is a botocore `StreamingBody`. There is no test covering the `storage_backend == "s3"` branch (`grep` shows only local/store tests), boto3 isn’t even installed in the venv (tests pass without it), and `StreamingBody` iteration semantics under Starlette are version-dependent. Add a test with a fake S3 client returning a file-like body, and consider wrapping with `response["Body"].iter_chunks()` explicitly. Also the `except Exception` collapses config/permission errors into a 404.

### Low / Info

**L1 — `get_settings()` is `@lru_cache`d but drives provider/backend selection**
`ocr_provider.get_ocr_provider`, `ad_extraction.configured_llm_provider`, and `TextractOCRProvider.__init__` all read cached settings. Tests call `get_settings.cache_clear()`, but in a long-running process env/secret changes won’t take effect without restart. Acceptable if intentional; note it.

**L2 — OpenAI AD extraction trusts model-returned `sourceUrls`**
`backend/app/services/ad_extraction.py` `OpenAIResponsesADExtractionProvider.extract` feeds `record.html_url`/`pdf_url`/excerpts into the prompt and stores model-produced `sourceUrls` in the extraction output. There’s no domain allowlist (e.g. federalregister.gov/faa.gov) on returned URLs, and this data feeds airworthiness compliance. Mitigated by review gating (`LLM_REVIEW_THRESHOLD`, disagreement reasons), but consider validating returned URLs before they’re surfaced to users.

**L3 — Unhandled IntegrityError on tag uniqueness**
Migration `20260708_0008` adds unique indexes on `organizations.customer_account_tag` and `aircraft.cost_allocation_tag`. `ensure_*_tag` fallbacks are id-derived (unique), but a user-supplied colliding tag would surface as an unhandled 500 rather than a validation error. Low likelihood given current write paths.

**L4 — docker-compose bind-mount inconsistency**
`backend/docker-compose.yml` adds `volumes: - .:/app` to `migrate` and `worker` but not `api`. Harmless for dev, but inconsistent (api won’t hot-reload source).

**L5 — `decode_possible_utf16` order change**
`drs_bulk_import.py` reordered decode attempts to try `utf-8` first. With `errors="ignore"`, a genuine UTF-16LE Access blob decoded as UTF-8 first could silently produce partial/garbled text instead of falling through. This only affects the binary-scan fallback path (already flagged as degraded/`partial`), so low impact, but the `errors="ignore"` means the loop never actually raises `UnicodeError` — every branch after the first “succeeds,” so ordering fully determines the result.

## 2. Open Questions

1. **Consent intent (H2):** Is `pilotConsentAccepted` a legal gate for processing volunteer data, or purely a billing flag? That determines whether the backend must reject `false`.
2. **Runtime least-privilege roles:** `main.tf` provisions the ECS cluster, ECR, logs, and buckets but **no ECS task/execution roles or task definitions**. The review context mentions “least-privilege runtime roles” — are those intended for a later PR? Right now nothing constrains what the app role can do against S3/Textract.
3. **State bucket bootstrap:** `versions.tf` points the backend at `paprnav-pilot-terraform-state-527257972989`, which `main.tf` also *creates*. Is the chicken-and-egg bootstrap (local state → migrate) documented/handled, given `terraform.tfstate` is currently local?
4. **Textract page cost vs. `billable_page_count`:** `run.billable_page_count = len(result.pages)` is set even when `billing_status == "not_billable"`. Intended (record volume regardless), or should it be gated on consent?
5. **Model name `gpt-5.5`:** `config.py` / `.env.example` default `PAPRNAV_AD_EXTRACTION_MODEL=gpt-5.5`. Is that a real model id for the target OpenAI account, or a placeholder?

## 4. Brief Summary

Solid, well-tested backend work: the storage/OCR/AD-extraction provider abstractions are clean, the cost-tag model is coherent, and the DRS mdbtools import with snapshot status/issue tracking is a real improvement. The main things to address before shipping the pilot are: enforce consent server-side (H2), tighten the KMS grant in the deploy policy (H1), fix the Terraform version floor for `use_lockfile` and the S3 noncurrent-version lifecycle (M1/M2), and reconcile the cost-allocation-tag expectations with how AWS billing (especially Textract) actually works (M3). Add coverage for the S3 download path (M4). No committed secrets or state; local defaults remain `local`/`deterministic`, so CI/dev stay safe.
