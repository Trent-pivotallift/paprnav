# Review: Layout-First OCR Pipeline & OCR Workflow Decisions

## 1. Findings

### High

**`backend/requirements.txt:11` — `Pillow>=12.1,<13` cannot install on Python < 3.10, and this is now a mandatory (not optional) dependency.**
Verified with a clean venv: PyPI's `12.0.0`–`12.3.0` Pillow releases all declare `Requires-Python >=3.10`, so `pip install -r requirements.txt` fails outright on Python 3.9 (`ERROR: No matching distribution found for Pillow<13,>=12.1`). The repo pins no Python version anywhere (no `.python-version`, no README floor — it just says `python -m venv .venv`), and the checked-in dev `.venv` in this repo is Python 3.9.6. The production `Dockerfile` uses `python:3.12-slim` so it's unaffected, but any local/CI machine on 3.9 will fail setup immediately. Per the review context ("local defaults should remain safe for development and CI"), this is a real regression, and Pillow was added to `requirements.txt` (used by the base API image) rather than being isolated in `requirements-layout-ocr.txt` as the stated policy ("keep the model stack out of the ordinary API image") suggests it should have been, or at minimum the version floor should be compatible with the project's actual minimum Python.

### Medium

**`backend/app/services/layout_first_ocr.py` — no "estimated internal cost" is recorded, contradicting D019's own integration contract.**
`.ai/DECISIONS.md` D019 explicitly requires preserving "billable page count, latency, hardware/channel metadata, **and estimated internal cost**." `LayoutFirstVLMOCRProvider.process_upload`'s `metadata` dict (lines 251‑267) has `provider_mode`, `provider_channel`, `layout_model`, `recognition_model`, `recognition_confidence_available`, `third_party_processing`, `processing_latency_ms` — no cost field. Compare with `MistralOCRProvider` (`ocr_provider.py:754-755`), which sets `estimated_unit_cost_usd_per_page` / `estimated_cost_usd`. This gap is directly visible in `run_ocr_feasibility.py`'s `summarize_job`, which reads `ocr_metadata.get("estimated_cost_usd")` — for layout-first runs this will always be `null`, undermining the account/aircraft cost-allocation reporting that's central to the AWS-pilot billing requirement.

**`backend/app/services/ingestion.py:427-428` — `is_ignorable_logbook_line` now treats any multi-line text as never-ignorable, which can let a pure-header REGION_ span become a spurious empty logbook entry.**
Traced the path: if a detected region contains only boilerplate (e.g., `"YEAR\nDATE\n..."`) with no real signal and is the *only* region on a page, it still passes the `entry_drafts_from_page` span filter (multi-line ⇒ never ignorable), no anchor is found, and `draft_from_line_cluster`/`build_entry_description` filters every individual line away, producing an entry with `description=""`, `entry_date=None`. It still gets created and pushed to review. This exact class of case (malformed/empty-content regions) is already called out as untested in `.ai/OCR_FEASIBILITY_STATUS.md` Loop 2 ("failure-fixture closure remains"), so it's a *known*, tracked gap — but it is concretely reachable in the current code, not just theoretical.

**`backend/app/services/ingestion.py:579-592` — `strip_date`'s new `match.start() <= 16` heuristic is a magic-number position guess, not tied to the actually-extracted anchor date.**
This correctly fixes the previously-reported bug (AD-reference dates like `AD 11-10-09` getting stripped from descriptions), and the two added tests pass. But the guard is a raw re-search of the text by character offset, independent of which match `parse_date` actually chose as the entry's date. For layout-first regions that concatenate multiple original fields onto one line, a legitimate leading date preceded by a long label (>16 chars) will be left un-stripped and duplicated in `description`, while an AD-reference occurring before column 16 could still be wrongly stripped. Only the two hand-picked examples are covered by tests; no fixture exercises either false-positive/false-negative direction of this 16-char cutoff.

### Low

**`backend/app/services/layout_first_ocr.py:459-486` / `validate_layout_region` — polygon geometry is never validated, only bbox is.**
`validate_layout_region` (lines 504‑526) checks bbox range/overflow but not `region.polygon` (arbitrary point count, no 0–1 range or consistency-with-bbox check). Currently low risk because the frontend doesn't render `polygon` yet (no references found under `frontend/src`), but D019 lists polygon evidence as part of the required contract, and there's no fixture for "malformed/overlapping regions" as the status doc itself notes is still pending.

**`normalize_layout_confidence` (`layout_first_ocr.py:497-501`) infers 0–1 vs 0–100 scale purely from `value <= 1`.**
A genuine raw score of `1` on an actual 0–100 scale would be silently reinterpreted as `100`. Low impact given the documented PP-DocLayout output is 0–1, but it's an unverified assumption with no defensive check/log.

## 2. Open Questions

- Is the GLM-OCR "model is MIT" licensing claim in `.ai/PROVIDER_REFERENCES.md` independently confirmed against the actual model card, or taken from the project's own README? Vision/OCR model licenses often carry usage restrictions beyond the code license — worth double-checking before any use beyond local feasibility.
- `span_requires_raw_ocr_correction` (`ingestion.py:409-414`) only matches `span_type == "LINE"`, so `REGION_*` spans never trigger the per-span `awaiting_ocr_corrections` review step, relying entirely on entry-level `needs_review` gating later. Is that the intended review flow for layout-first output, or should there be an equivalent "confidence unavailable ⇒ requires review" gate at the span-correction stage too?
- Should a minimum Python version (3.10+) be declared/enforced repo-wide (e.g., `.python-version`, README note, CI matrix) now that a dependency implicitly requires it, rather than leaving it to whatever `python` a given machine resolves to?
- Is `glmocr[layout]==0.1.5` (and the associated Ollama model weights) subject to any supply-chain/provenance review before it's used even locally, given it's a narrowly-adopted third-party package pulling in model binaries?

## 3. Verification Notes

- Ran the full backend suite: `PYTHONPATH=. .venv/bin/pytest -q` → 52 passed, but only after manually installing Pillow into `.venv` (Python 3.9.6) with no version pin — confirms tests don't exercise the actual pinned `Pillow>=12.1,<13` constraint.
- Reproduced the requirements.txt install failure in a clean venv: `pip install -r requirements.txt` fails with `No matching distribution found for Pillow<13,>=12.1` on Python 3.9.6; `pip index versions Pillow` confirms 12.x requires Python ≥3.10.

- Confirmed `backend/Dockerfile` only installs from `requirements.txt` (not `requirements-layout-ocr.txt`), so the heavy GLM/PP-DocLayout stack correctly stays out of the production image, consistent with the stated decision — only the Pillow addition crosses that boundary.
- No Terraform/IaC files are touched by this change set; AWS/IAM review scope doesn't apply here.
- Did not have Ollama/PP-DocLayout installed, so the actual layout-first pipeline was not exercised end-to-end — only the unit tests using fakes (`FakeLayoutDetector`/`FakeRegionRecognizer`/`FakeHTTPClient`) were run.

## 4. Brief Summary

The doc updates (D018/D019, feasibility status, provider references) are coherent and appropriately cautious (Textract remains baseline, Mistral direct processing stays disabled, local-only Ollama endpoint enforced). The new layout-first provider is well-isolated behind the existing `OCRProvider` interface with reasonable security defaults (loopback-only Ollama, path-traversal-guarded local storage reads, matching the existing Textract/Mistral providers' patterns). The main concrete problem is the `Pillow` version pin breaking `pip install -r requirements.txt` on Python <3.10 environments that aren't excluded anywhere in the repo — this should be fixed before merge. The remaining findings (missing cost metadata, the multi-line ignorable-line exemption, and the `strip_date` position heuristic) are real but narrower correctness/completeness gaps, several of which the project's own status doc already tracks as pending fixture work.
