## Blocking findings

**1. ALB path routing will break every frontend→backend API call (highest priority, spans `load_balancer.tf` + the Next.js proxy route)**
- `aws_lb_listener_rule.api` forwards **any** path matching `/api/*` straight to the FastAPI target group (`load_balancer.tf:70-84`).
- The frontend's own reverse-proxy handler lives at `src/app/api/backend/[...path]/route.ts`, and `NEXT_PUBLIC_PAPRNAV_API_BASE_URL` defaults to `/api/backend` (`ecs_runtime.tf:223`, `lib/api.ts:1`). Browser calls therefore hit `/api/backend/api/v1/...`, which also starts with `/api/` — the ALB will intercept it and forward it directly to the API container as `/api/backend/api/v1/...`, a path FastAPI never registers (routes are `/api/v1/...`, confirmed via each router's `prefix=`). Every authenticated call, upload, and ingestion request would 404 once this is deployed live, even after images/secrets are all in place. The frontend's own internal proxy route would never be reached because the ALB diverts the request before it gets to the frontend container.
- Fix direction: either give the frontend proxy a path prefix outside `/api/*` (e.g. `/app-api/backend/...`) or scope the ALB rule to the backend's real prefix (`/api/v1/*`) and have the frontend call the backend directly without proxying through `/api/*`.

**2. `NEXT_PUBLIC_PAPRNAV_API_BASE_URL` is wired as an ECS *runtime* env var but Next.js inlines `NEXT_PUBLIC_*` at build time**
- `ecs_runtime.tf` sets `NEXT_PUBLIC_PAPRNAV_API_BASE_URL` in the frontend task definition's `environment` block (line 223). Standard Next.js production builds bake `NEXT_PUBLIC_*` values into the client bundle at `next build` time; setting it as a container runtime env var has no effect on the shipped JS unless the (currently missing) frontend Dockerfile explicitly re-injects it as a build `ARG`/`ENV` before `next build`. `PAPRNAV_BACKEND_URL` (no `NEXT_PUBLIC_` prefix, consumed only server-side inside `route.ts`) is fine at runtime — but the client-facing var is not. This needs to be resolved as part of writing the still-missing frontend Dockerfile, or the client will silently ship with whatever value was baked in at image build time (possibly `undefined`/wrong).

**3. No TLS anywhere — ALB is intentionally HTTP-only and session cookies are proxied over it**
- `aws_lb_listener.http` is the only listener (port 80), no ACM cert/HTTPS listener/redirect exists. The frontend proxy forwards the `cookie` header for session auth (`route.ts:26,30`), and the app has a `session-secret` Secrets Manager entry, implying cookie-based auth. Once this is used for anything beyond an internal smoke test, real volunteer PII (logbook entries) and session cookies travel in plaintext, both browser→ALB and ALB→backend/frontend containers. This must be closed (ACM cert + HTTPS listener + HTTP→HTTPS redirect, `Secure`/`SameSite` cookie flags) before inviting any external volunteer, matching the same caution already given in the docs for Textract budget risk.

**4. Worker has a task definition but no execution path at all**
- `aws_ecs_task_definition.worker` exists, but there is no `aws_ecs_service`, no EventBridge Scheduled Task, no Fargate scheduled rule anywhere in the reviewed files. `backend/app/workers/ocr.py` is a run-once batch script (drains queued jobs then exits), so an ECS Service (long-running) isn't even the right primitive — it needs a scheduled/one-shot task trigger. As written, once images are pushed there is still no mechanism that ever runs OCR processing; someone would have to `aws ecs run-task` manually every time. This is a functional gap, not just a "raise desired_count later" story, and should be called out as unfinished rather than implied-complete by the IAM/task-definition work.

**5. Secrets are empty placeholders with no population mechanism or drift protection**
- `aws_secretsmanager_secret.database_url` and `.session_secret` are created with no `aws_secretsmanager_secret_version`. That's correct for not committing secrets to state/git, but `manage_master_user_password = true` puts the *actual* RDS password in a separate AWS-managed secret. Nothing here documents or automates deriving `DATABASE_URL` from `aws_db_instance.postgres` attributes + the managed secret, so a human must manually assemble and paste a full connection string (including a live DB password) via CLI — error-prone and undocumented as an exact runbook step in these files. Worse, if/when the managed master password rotates, this static `DATABASE_URL` secret goes stale with no re-sync, causing a silent outage. At minimum this needs an explicit runbook or automation (e.g., a small Lambda/rotation hook, or a documented `aws secretsmanager put-secret-value` sequence tied to the RDS secret) before flipping `api_desired_count`/`frontend_desired_count` off 0.

**6. Confirmed deployability blockers already documented, worth re-flagging as real gates, not just notes**
- ECR repos empty (`[]` for both repos) and no frontend Dockerfile — confirmed accurate. Backend `Dockerfile` also has no migration step (`CMD` runs `uvicorn` directly), and no one-off "migrate" task definition exists in `ecs_runtime.tf`, so first deploy still needs an undocumented manual `alembic upgrade head` execution path (e.g., a scheduled/one-off ECS task) that isn't defined anywhere.
- Both `api` and `worker` task definitions reference `${aws_ecr_repository.api.repository_url}:latest`, and the ECR repos are `image_tag_mutability = "MUTABLE"`. Mutable `:latest` gives no reproducible/rollback-safe deployments and Terraform has no way to detect an image content change to force a new ECS deployment — this should move to immutable, commit-SHA-tagged images before real use.

## Questions

1. Is the intent to keep API/frontend ECS tasks in the **public** subnets permanently (no NAT gateway), with private subnets reserved solely for RDS? If so, can the README be updated to state this as a deliberate cost/security tradeoff rather than leaving it implicit — since tasks currently only avoid direct internet exposure because of the `ecs_tasks` security group, not network isolation?
2. What is the actual plan for invoking the worker (EventBridge scheduled Fargate task? SQS-triggered run-task? manual cron on a bastion)? This affects whether a `aws_ecs_service`/`aws_scheduler_schedule` resource is still needed here.
3. Given `textract:StartDocumentTextDetection`/`GetDocumentTextDetection` are granted to the worker role but `TextractOCRProvider` only implements synchronous `DetectDocumentText` (confirmed in `ocr_provider.py`) with a documented 10MB/no-PDF limitation — is async S3-based Textract (mentioned in the status doc as required for real logbook PDFs) planned before this runtime skeleton is applied with `desired_count > 0`, or is sync-only intentionally the pilot's initial capability?
4. Is there a plan to scope the `api_task`/`worker_task` S3 IAM policy to the `uploads/` (and relevant tmp/derived) prefixes rather than `${bucket_arn}/*` for the whole artifacts bucket, given `PAPRNAV_S3_UPLOAD_PREFIX=uploads` is already used as a logical boundary?
5. Should RDS have `multi_az = true` for the pilot, or is single-AZ an accepted cost/availability tradeoff that should be stated explicitly in the README next to the deletion-protection/backup notes?

## Verification notes

- `final_snapshot_identifier` uses `timestamp()` directly in the resource, but `lifecycle.ignore_changes = [final_snapshot_identifier]` correctly suppresses the perpetual diff this would otherwise cause on every plan — confirmed not a bug.
- RDS is not publicly accessible, sits in the private subnet group, storage is encrypted, and the master password is AWS-managed (not stored in a static variable/state) — good baseline.
- Public/private subnet security groups are scoped correctly at the SG layer (ALB ingress only 80/0.0.0.0/0, ECS tasks only accept from the ALB SG on the two app ports, RDS only accepts 5432 from the ECS tasks SG) — no obvious 0.0.0.0/0 leaks into ECS or RDS ingress.

- S3 buckets (artifacts, terraform state) block public access, use SSE, and versioning is enabled; state files (`*.tfstate*`) are correctly gitignored and not tracked despite being present on disk.
