# Findings

Ordered by severity. File:line references are from the working tree.

## Confirmed Issues

**1. (Medium) `MistralOCRProvider` never populates `processing_seconds`, breaking cross‑provider usage metering**
`backend/app/services/ocr_provider.py:670-815` — `MistralOCRProvider.process_upload()` calls `self.result_from_response(response)` directly and returns immediately; unlike `TextractOCRProvider` (which wraps every code path through `_with_usage_metadata`, `ocr_provider.py:298-330`) and `LayoutFirstVLMOCRProvider` (`layout_first_ocr.py:248-282`), Mistral's `metadata` dict never contains a `processing_seconds` key. In `ingestion.py:120-135`, `metadata_float(result.metadata, "processing_seconds")` will therefore silently store `run.processing_seconds = None` for every real Mistral OCR run.
This directly contradicts `.ai/DECISIONS.md` D020 ("All providers write usage to `OCRRun` with … elapsed processing time …") and `.ai/OCR_FEASIBILITY_STATUS.md` ("Provider-neutral usage metering is now first-class on `OCRRun` … processing seconds"). It's not caught by any test — `test_ocr_provider.py`'s Mistral test only asserts `pricing_unit`/`pricing_rate_usd`/`estimated_cost_usd`, never `processing_seconds`.
Impact is currently low (Mistral direct-API processing of real customer docs is policy-disabled), but this is exactly the kind of billing/cost gap that should be closed before Mistral is ever promoted, and it silently violates the documented invariant today.

**2. (Medium) `Float` used for money columns**
`backend/app/models/core.py:296-299` and the new migration (`20260725_0011_add_ocr_usage_metering.py:21-36`) add `pricing_rate_usd` and `estimated_cost_usd` as `Float`. These are documented as "estimated" costs (not invoices), so this may be an accepted tradeoff for the feasibility stage, but IEEE-754 floats will accumulate rounding error if these columns are later summed/aggregated for real cost reporting or reconciliation against AWS billing. Worth a decision note if this data is expected to roll up into actual account-level cost dashboards; `Numeric`/`Decimal` would be safer for anything approaching billing accuracy.

**3. (Low/Medium) Repeated full re-parsing of maintenance text per (directive × entry) pair with no caching**
`backend/app/services/ad_matching.py:355-366` — `rank_candidate_entries()` is invoked once per approved directive that survives the applicability filter (`match_aircraft_ads`, `ad_matching.py:57-73`), and for *every* candidate directive it re-runs `extract_structured_maintenance_data()` (a chain of several regex scans) against every candidate logbook entry, even though the entry text does not change across directives. For an aircraft with a non-trivial number of applicable ADs (post‑DRS-bulk-import catalogs can easily have dozens to low‑hundreds of ADs per airframe/engine/prop combination) and a multi-decade logbook, this is O(directives × entries) regex work recomputed from scratch on every `match_aircraft_ads` call. This is a compute-cost concern (ties directly to ECS worker billing) more than a correctness bug — worth memoizing structured extraction per `entry.id` (e.g., a dict computed once before the directive loop) before running this at fleet scale.

## Positive/Notable Safety Improvements (confirmed correct)

These are worth calling out explicitly since they're the core of the "false-positive safety" focus and they are implemented correctly and covered by tests:

- `classify_match_type()` now always appends `"recurring_due_status_unknown"` when `complianceIntervals` is present (`ad_matching.py:410-424`), which permanently routes `simple_recurring` AD matches to `needs_adjudication` until due-status calculation exists. Verified by `test_ad_matching_creates_evidence_and_unresolved_review_tasks` (previously asserted `candidate_satisfied`, now asserts `needs_adjudication` + the new reason).
- `candidate_satisfied` now requires all three of: an explicit normalized AD-number match (`explicit_ad_reference`), a parsed disposition of `complied`/`inspected` (not `mentioned`/`not_applicable`/None), and `entry.review_status == "verified"` (`ad_matching.py:130-146`). Plain keyword/substring AD-number hits without a parsed compliance claim are downgraded to a weak signal (`0.45` vs `0.82`) and always forced into `needs_adjudication` via `explicit_ad_reference_missing`. Well covered by the new `test_ad_matching_normalizes_legacy_ad_numbers_and_requires_verified_claims`.
- `EXPLICIT_AD_PATTERN` in `maintenance_extraction.py:10-13` requires a literal `AD` token immediately preceding the number, so ordinary dates (e.g. `12-17-12`) are never mistaken for AD references — verified by `test_extracts_explicit_ad_reference_without_treating_dates_as_ads`.
- Two/four-digit AD-year normalization (`ad_identity.py`) is now applied uniformly on both the directive's `adNumber` and every parsed logbook AD reference before comparison, so `AD 11-10-09` in a logbook correctly matches directive `2011-10-09` — verified.
- The `ingestion.py:348` low-confidence gate bug is fixed: previously `(span.confidence or 0) < 80` treated *any* span with `confidence=None` (including non-`LINE` structural spans such as `TABLE`/`CELL`, and now layout-first `REGION_*` spans) as low-confidence, which would have forced every analysis-mode/layout-first job into `awaiting_ocr_corrections`. The new `span_requires_raw_ocr_correction()` (`ingestion.py:493-503`) correctly scopes this to `LINE` spans with a real sub-threshold numeric confidence.
- Nullable confidence is propagated correctly end-to-end: `OCRSpanResult.confidence: Optional[float]`, `min_confidence: float | None` on drafts, and `extract_entries_from_job` only marks an entry `verified` when `draft.min_confidence is not None and draft.min_confidence >= LOW_CONFIDENCE_THRESHOLD` (`ingestion.py:275-284`). Layout-first regions (which always report `confidence=None`) therefore always land in `needs_review`, never falsely `verified` — verified by `test_region_spans_split_two_entries_and_preserve_absent_times_as_null` and `test_region_without_recognition_confidence_uses_candidate_review`.
- Local layout-first cost conversion (`layout_first_ocr.py:248-250`, `estimated_cost = processing_seconds / 3600 * compute_rate`) defaults `PAPRNAV_LAYOUT_FIRST_COMPUTE_RATE_USD_PER_HOUR=0` (`config.py`, `.env.example`), so local/CI runs always compute `estimated_cost_usd == 0` unless an operator explicitly configures a rate — a safe default. Same pattern for `PAPRNAV_TEXTRACT_ESTIMATED_UNIT_COST_USD_PER_PAGE=0`.
- `OllamaGLMRegionRecognizer` / `validate_loopback_ollama_url()` (`layout_first_ocr.py:454-464`) strictly allowlists `127.0.0.1` / `::1` / `localhost` hostnames, preventing the local-OCR path from being pointed at an arbitrary remote endpoint (SSRF-style misconfiguration) — good defensive control for a feature that will eventually run with AWS credentials/network access nearby.

## Open Questions

- Is Mistral's fixed `direct_api_page_price_usd = 0.004` (`ocr_provider.py:645`) class constant intentionally not configurable via env, unlike Textract's and layout-first's rates? If Mistral pricing changes, this requires a code change/redeploy rather than a config update — worth confirming that's acceptable given it's currently policy-disabled for real customer traffic anyway.
- For `is_potentially_applicable()` fallback path (`ad_matching.py:242-260`, unchanged by this diff) — when a directive has no structured `target_applicabilities`, applicability is decided by loose substring/term overlap between `affectedProducts` and aircraft make/model/engine/prop strings. Given AD matching is now much stricter downstream, is it intentional that the *applicability* gate itself remains comparatively loose? (Not a regression introduced by this diff, but worth confirming it's on the roadmap.)
- `strip_matching_date()` / `strip_date()` (`ingestion.py:687-732`) only strip the *first* occurrence of the entry's own date from the description, once per cluster. Is it expected that a duplicate date mentioned a second time in the same cluster remains in the description text? (Tests only exercise a single occurrence, so this is unverified either way — not clearly wrong, just unconfirmed intent.)
- `run.cost_allocation_tags` merges the *entire* `result.metadata` dict (including provider-internal fields like `textract_block_counts`, `layout_model`, `recognition_model`, etc. — pre-existing behavior, not new to this diff) into the JSON column that's also used for customer/account/aircraft billing tags. Is this JSON field intended to double as "all provider metadata" storage, or should provider/debug metadata be split from billing-tag data as the schema matures? Not introduced by this change, but the new pricing fields make the column's dual purpose more visible.

# Brief Summary

The OCR-metering and nullable-confidence changes are well-designed and consistently defensive: nullable recognition confidence correctly prevents auto-verification, the low-confidence review gate bug is fixed, and local/AWS cost-rate defaults are zero-safe. The AD matcher changes are the strongest part of this diff — recurring ADs are now unconditionally routed to human adjudication, and one-time AD "candidate_satisfied" status now requires an explicit normalized AD reference, a parsed compliance/inspection claim, and a verified logbook entry, closing a real false-positive risk; this is covered by solid new tests. The main gap is that the new provider-neutral usage-metering contract (as stated in `.ai/DECISIONS.md` D020) is not actually met by `MistralOCRProvider`, which never records `processing_seconds`. A secondary, lower-priority concern is unmemoized per-directive re-parsing of logbook text in the AD matcher, which could become a real compute-cost issue as the AD catalog and logbook history grow.
